> **VmPeak is not usable as the paper's metric here.** The ASan builds report VmPeak in the terabyte range: the one-eighth shadow reservation is mapped as PROT_NONE and counted in VmSize, but untouched pages are never resident. Peak RSS (VmHWM) is the comparable quantity; the VmPeak column is kept to document the effect.

> Checksums are identical across modes for every benchmark, so the instrumented builds computed the same results.

## What each workload does and does not measure

- **`b1_allocs`** — allocation-only loop: tiny malloc/free pairs with almost no other work. It is an upper bound on allocator overhead, not a stand-in for perlbench, which spends most of its time outside malloc. A large ratio here is expected and is not evidence against the paper.
- **`b2_pointer`** — dependent-load chain over a heap linked list; isolates the extra shadow load per dereference.
- **`b3_int`** — byte-at-a-time hashing; isolates 1-byte access instrumentation.
- **`b4_float`** — dense double-precision arrays. The measured ratio is dominated by *de-vectorisation* (instrumented loops cannot be vectorised), not by shadow checks, so it is not a clean test of the paper's claim that floating-point code pays the least.
- **`b5_string`** — byte-wise token scan; the closest analogue to the paper's text-processing cases.
